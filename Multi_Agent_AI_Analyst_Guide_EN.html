A team of AI agents — a supervisor that plans and delegates to specialists (documents, web, database, code), a critic that verifies the work, plus an evaluation and observability layer that proves it works. The challenge — why one agent isn't enough

A single RAG agent can only retrieve and answer. But a real question — "How many customers churned last quarter, and why?" — needs a database query (the number), document retrieval (the reasons), and maybe a calculation. No single tool answers it. A multi-agent system divides the work: a supervisor routes to the right specialist, collects results, and a critic verifies before answering — looping back if it's wrong.

Visual dictionary

Multi-agent system

Several specialised agents that collaborate on one task instead of one agent doing everything.

Supervisor / Router

The "manager" agent: reads the question and decides which specialist runs next.

Specialist agent

An agent with one job — retriever, web-searcher, data analyst, or code runner.

Tool use

Giving an agent real actions — run a query, execute Python — not just generate text.

Text-to-SQL

The agent writes a SQL query from a plain question, runs it, and reads the result.

Code agent

An agent that writes and runs Python for calculations, tables, or charts.

Agent handoff

Passing control and shared state from one agent to another through the graph.

Critic / Verifier

Checks the final answer for correctness and grounding, and forces a revision if it's wrong.

Long-term memory

A vector store of past turns so the system remembers earlier context.

LLM-as-judge

Using a strong model to score another model's answers against a rubric or reference.

RAGAS

A library of RAG metrics: faithfulness, answer relevance, context precision/recall.

Observability (Langfuse)

Tracing every agent step, tool call, token and cost so you can debug and measure.

A. Build order — what to build first (and why)

Build in this order. Each phase depends on the one before it — you cannot route to agents that don't exist yet, and you cannot evaluate a system that doesn't run yet.

Phase 1 · Foundation — Features 1–2: shared state, config & keys, then document ingestion + vector store.
Why first: everything reads/writes the shared state, and the retriever needs a populated vector store to exist.
Phase 2 · Specialist agents (one at a time) — Features 3–6: retriever → web → data (SQL) → code. Build and test each agent alone before wiring them together.
Why next: the supervisor has nothing to route to until the specialists work. Test each in isolation first.
Phase 3 · Orchestration — Features 7–9: the supervisor (router), the critic (verifier), then wire the LangGraph graph.
Why now: only once the agents work can the supervisor delegate to them and the critic verify their output.
Phase 4 · Memory & Evaluation — Features 10–11: long-term memory, then the evaluation harness (RAGAS + LLM-judge).
Why now: you can only measure a system that already runs end-to-end.
Phase 5 · Observability, Frontend & Deploy — Features 12–14: Langfuse tracing, streaming frontend, then deploy both.
Why last: these wrap a working, measured system for real use.

B. Features in detail

Each feature below has: What it is · Why it matters · How to build it · Done when (the checkable outcome) · Watch out.

F1Shared state & configPhase 1

What: one AgentState object that flows through every node, plus a config that reads keys from .env.

Why: every agent reads and updates the same state (question, documents, results, steps, revision count). No shared state = no collaboration.

class AgentState(TypedDict):
    question:str; plan:str; documents:List[str]
    sql_result:Optional[str]; code_result:Optional[str]
    answer:str; steps:List[str]; revisions:int
Done when: keys load from .env; the state type is defined and used by every node.
Watch out: never commit .env. Keep revisions in state so the graph can terminate.
F2Ingestion & vector storePhase 1

What: load documents → chunk → embed → store in Qdrant.

Why: the retriever agent has nothing to search until documents are embedded and stored.

chunks = RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=150).split_documents(docs)
vectorstore.add_documents(chunks)
Done when: a document is ingested and a similarity search returns relevant chunks.
Watch out: the embedding dimension must match the Qdrant collection size.
F3Retriever agentPhase 2

What: the RAG agent — retrieves the top-k relevant chunks for the question.

Why: it answers "from your documents" questions; the reused core from the previous project.

def retriever_agent(state):
    docs = vectorstore.as_retriever(search_kwargs={"k":4}).invoke(state["question"])
    return {"documents":[d.page_content for d in docs], "steps":state["steps"]+["retriever"]}
Done when: tested alone, it returns correct chunks for a document question.
F4Web agentPhase 2

What: a Tavily web-search agent for questions outside the documents.

Why: extends coverage beyond the local knowledge base.

def web_agent(state):
    hits = TavilyClient(api_key=KEY).search(state["question"])["results"]
    return {"documents":state["documents"]+[h["content"] for h in hits]}
Done when: it returns live web results; skips gracefully if no key is set.
F5Data agent — Text-to-SQLPhase 2

What: the hard new skill — the agent writes a SQL query from the question, runs it on a real database, reads the result.

Why: numeric/aggregate questions ("how many…", "average…") can only be answered by querying data, not by RAG.

db = SQLDatabase.from_uri("sqlite:///data/company.db")
def data_agent(state):
    sql = llm.invoke(f"Schema:\n{db.get_table_info()}\nOne SQLite query for: {state['question']}. SQL only.").content
    assert sql.strip().lower().startswith("select")   # read-only guard
    return {"sql_result": f"{sql}\n→ {db.run(sql)}", "steps":state["steps"]+["data(sql)"]}
Done when: a "how many…" question returns the correct number from the database.
Watch out: read-only DB user; reject any query that isn't a SELECT. Never let it run DROP/DELETE.
F6Code agent — run PythonPhase 2

What: writes and executes Python for calculations, aggregation, or charts.

Why: LLMs are unreliable at exact math; running code gives correct numbers.

py = PythonREPLTool()
def code_agent(state):
    code = llm.invoke(f"Write Python to answer: {state['question']}. print() the result.").content
    return {"code_result": py.run(code), "steps":state["steps"]+["code"]}
Done when: a math/aggregation question returns the correct computed answer.
Watch out: run in a sandbox with a runtime cap — never execute model-written code on the bare server.
F7Supervisor / RouterPhase 3

What: the manager — an LLM with structured output that decides the next agent, or that the answer is ready.

Why: this is the brain of a multi-agent system; it turns four separate agents into a team.

class Route(BaseModel): next:str = Field(description="retriever|web|data|code|finish")
def supervisor(state):
    d = llm.with_structured_output(Route).invoke(
        f"Question:{state['question']} Collected:{state['steps']}. Next agent, or 'finish'.")
    return {"plan":d.next, "steps":state["steps"]+["supervisor→"+d.next]}
Done when: for a SQL question it routes to data; for a doc question to retriever; it eventually chooses finish.
F8Critic / VerifierPhase 3

What: checks the drafted answer against the gathered evidence; approves or sends it back to revise.

Why: catches wrong or unsupported answers before the user sees them — the quality gate.

class Verdict(BaseModel): ok:bool; reason:str
def critic(state):
    v = llm.with_structured_output(Verdict).invoke(
        f"Q:{state['question']} Evidence:{state['documents']}{state['sql_result']}{state['code_result']} "
        f"Answer:{state['answer']} Correct AND fully supported?")
    return {"revisions":state["revisions"]+(0 if v.ok else 1)}
Done when: a deliberately wrong answer is caught and revised; a good one is approved.
F9Supervisor graph (wiring)Phase 3

What: the LangGraph graph connecting supervisor → agent → back to supervisor, then critic → finish or revise.

Why: this is what makes it a system, not a pile of functions.

g.add_conditional_edges("supervisor", lambda s:s["plan"],
   {"retriever":"retriever","web":"web","data":"data","code":"code","finish":"generate"})
for a in["retriever","web","data","code"]: g.add_edge(a,"supervisor")
g.add_conditional_edges("critic", route_after_critic, {"finish":END,"revise":"supervisor"})
Done when: a multi-part question runs end-to-end through several agents and terminates with one answer.
Watch out: set a recursion/step limit so a mis-routing loop can't run forever.
F10Long-term memoryPhase 4

What: a vector store of past turns; relevant history is fed into the supervisor.

Why: lets the system answer follow-ups that depend on earlier turns.

memory.add_texts([f"Q:{q}\nA:{a}"])                # after each turn
past = memory.similarity_search(new_question, k=3)  # into the supervisor
Done when: a follow-up like "and the previous year?" uses the earlier context correctly.
F11Evaluation harnessPhase 4

What: a fixed test set scored automatically with RAGAS metrics and an LLM judge.

Why: the difference between a demo and a product — you can measure quality, not just eyeball it.

from ragas import evaluate
from ragas.metrics import faithfulness, answer_relevancy, context_precision
scores = evaluate(dataset, metrics=[faithfulness, answer_relevancy, context_precision])
# + LLM-judge: score each answer 1-5 vs a reference answer
Done when: running the harness prints a metrics table over a test set of at least 10 questions.
F12Observability (Langfuse)Phase 5

What: tracing of every agent step, tool call, token and cost.

Why: you can't debug or optimise what you can't see.

app.invoke(state, config={"callbacks":[CallbackHandler()]})  # every step traced
Done when: a Langfuse trace shows the full path (supervisor → data → code → critic) with token counts.
F13Streaming frontendPhase 5

What: a Next.js UI that streams the steps so users watch the agents work live.

Why: a multi-agent system is far more convincing when you can see which agent is acting.

Done when: the UI shows the live trace (supervisor → agent → critic → answer) with sources.
F14DeploymentPhase 5

What: make it a live, shareable link — a free option that needs no credit card:

Easiest (no card, no server): run the whole app + a Gradio UI in Google Colab and call demo.launch(share=True) — you get a public link for ~72 h. Colab has ~12 GB RAM, so even local embeddings fit.
Always-on API: deploy the backend to Render (free, no card) and the frontend to Vercel (free).

Why: a capstone must be a live URL — not just a notebook cell.

Done when: there is a public link (Gradio share or Render URL) that answers a real question.
Watch out: Render free is only 512 MB RAM — there, use API embeddings (Gemini), not a local model. Colab has plenty of RAM for local embeddings.

Final conclusion

A single agent answers. A team of agents plans, uses real tools, checks its own work, and proves it works. Build it phase by phase, and grade it feature by feature — by the end each student has shipped a supervisor-led system that queries databases, runs code, searches documents and the web, verifies its answers, and is measured with RAGAS and traced in Langfuse: the very front of what the field is doing today.
